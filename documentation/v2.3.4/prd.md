# v2.3.4 PRD: Error-Code Burn-Down, Figma Typings Bump & Safe Prototype-Reaction Editing

This document is the product / implementation spec for the **v2.3.4** release of `figma-edit-mcp`. It follows v2.3.3 (Plugin Type-Check Restoration & Safety-Contract Gap Closure) and has three tracks:

1. **Legacy error-code conversion.** Convert the plugin's legacy, uncoded failure surface to the structured error contract that v2.3.3 established, so that `UNKNOWN_ERROR` stops being the code for most of what the plugin can throw.
2. **Figma typings bump (`@figma/plugin-typings` 1.125.0 → 1.131.0).** Close the v2.3.3 Q35 residual: the pinned typings are behind the live Figma runtime, so the `SHADER` effect variant the runtime accepts is unreachable through `style_manage`. The bump also regenerates the typings-derived node-field inventory, which is why it is a release of its own rather than a late v2.3.3 edit.
3. **Lossless prototype-reaction reads and conflict-safe localized updates.** Repair `reaction_list` so it reports all native reactions and honest read coverage, then replace `reaction_update`'s caller-supplied whole-array overwrite with one state-checked localized operation per call.

> **Origin (Track 1).** The v2.3.3 Q16 resolution (2026-07-18, Option A — recorded in the [v2.3.3 PRD](../v2.3.3/prd.md) D9 code-inventory note, Rev 23) deliberately scoped error codes to messages that release added or edited. Everything older surfaces with the ratified legacy fallback `UNKNOWN_ERROR`: the message text travels intact, but no machine classification and no playbook entry exist. Q16's record names this release as the deferred conversion work and makes `UNKNOWN_ERROR` its burn-down metric.
>
> **Origin (Track 2).** The v2.3.3 Q35 resolution (2026-07-25, recorded in that PRD's D8 addendum and Rev 47) enumerated Figma's `Effect` union per variant, replacing a catchall that had been accepting unknown keys and silently discarding them. Enumeration is pinned to `@figma/plugin-typings` by a parity test, which makes the pinned version the contract — and live probing on 2026-07-26 (channel `zgkx`) showed the runtime is ahead of it: Figma's own validator lists a `SHADER` effect that `1.125.0` does not declare. v2.3.3 recorded that as an accepted residual with the typings bump as the named lever, and deferred the bump here because it drags in a regenerated node-field inventory that deserves its own review.
>
> **Origin (Track 3).** The v2.3.3 Q13 resolution removed `create_connection` and `reaction_to_connector_strategy` after live Design-file testing proved that a pasted FigJam `CONNECTOR` cannot be cloned in Figma Design. That decision deliberately retained `reaction_list` and `reaction_update` as the same-file native prototype surface, but review of their actual implementation found two independent Golden Rule failures: `reaction_list` silently filters every `CHANGE_TO` reaction and swallows missing/read-failed roots, while `reaction_update` accepts and replaces the caller's entire reactions array with no state token. v2.3.3 records those as deferred repairs rather than expanding its removal change into a second behavior rewrite.

## Release identity

> [!IMPORTANT]
> **This is v2.3.4.** It adds no new tools and changes no permission or scope behavior. Track 2 restores one capability the v2.3.3 enumeration made unreachable (`SHADER` effects) and may widen the set of node properties `node_info` can read, both as a consequence of the typings bump — neither is a new *power*, and both are called out in the CHANGELOG. Track 1 changes two things about failures only: the *shape* of thrown values (coded objects from the central registry instead of `Error` strings) and, where a message fails the v2.3.3 D9 acceptance check, the *text* of the message. The conditions under which Track 1 errors are thrown do not change — that is this release's equivalent of v2.3.3's "no runtime behavior change" rule for Track 1, and the same stop-and-escalate discipline applies: if an error conversion appears to require moving, adding, or removing a throw, stop and escalate rather than silently changing a live-verified control flow. Track 3 is the explicitly bounded exception: it changes the two existing reaction tools' read/write contracts under D9–D11 and is reviewed and tested independently.
>
> **It depends on v2.3.3 being merged first.** The central registry of message factories, the structured `{error: {code, message, details?}}` transport, the error playbook, and the `check:types:plugin`/`check:suppressions` gates are all v2.3.3 deliverables this release builds on. v2.3.3 Phase 8 rewrites `componentHandlers.ts`, and Phase 11 removes `connectorHandlers.ts` while moving reaction discovery into `prototypingHandlers.ts`; the v2.3.4 baseline and phase ownership below are measured after those changes.
>
> Version surfaces to bump follow the established mechanism (`package.json`, root `package-lock.json`, both `server.json` fields, root `manifest.json`, the plugin About handshake — enforced by `check:versions` and `check:plugin`): `2.3.3 → 2.3.4`. Patch level is consistent with the Q5 policy: this strengthens the failure contract without weakening any guarantee. Message-text changes are called out in the CHANGELOG because agents may currently match on prose — the codes this release adds are precisely the stable identifiers that make prose-matching unnecessary.

## The problem

v2.3.3's D9 made structured errors the contract, but scoped coding to messages it added or edited. The original 2026-07-18 inventory was 332 inline sites across 15 files. Rebased on the v2.3.3 Phase 11 removal (2026-07-30), the implementation baseline for this release is:

- **313 inline `throw new Error(...)` sites across 15 plugin files.** 49 of them wrap strings from the central `ERRORS` table (directly, via `formatScopeError`, or interpolated into a template literal); the remaining 264 compose their message ad hoc at the throw site. The net reduction from 332 is expected: v2.3.3 deleted the 20-site connector handler and moved the six-site reaction reader into `prototypingHandlers.ts`.
- **The central table itself is uncoded at the throw site.** `figma_plugin/utils/errors.ts` defines 28 keys (13 legacy plus 15 added by v2.3.3); handlers reference 12 of the legacy keys — but as message *strings* inside `new Error(...)`, so the key (the natural code) is discarded at the moment of throwing. This is what tempted the deleted prose-matching: the code existed, but only recoverable by matching text.
- **102 unit-test assertions match thrown message prose** (`toThrow("…")` and variants). Prose is the de-facto test contract, which makes every message improvement a test break and pushes implementers toward freezing bad messages.
- **One server-side legacy envelope convention.** `src/mcp_server/tools/channel.ts` reports join failures in-band as a *successful* tool result carrying `status: "error"` + `errorCode`/`errorMessage` fields — a convention that predates v2.3.3 D9's `isError: true` + `structuredContent` boundary. Two error surfaces now exist at the MCP boundary.
- **UI-relay local failures are flattened.** When `figma_plugin/ui.html`'s own dispatch catch fires, it forwards `error.message || "Error executing command"` — a string, with no code, indistinguishable from a plugin-authored failure.

Consequences for agents: every legacy failure arrives as `UNKNOWN_ERROR`, so the playbook cannot key an entry to it, the agent branches on prose, and message improvements are breaking changes. Consequences for contributors: new handler code copies the surrounding idiom (`throw new Error("…")`), so the uncoded surface grows.

### Track 2 — the pinned typings are behind the runtime

`package.json` pins `@figma/plugin-typings@1.125.0`; the current published version is `1.131.0`. Measured 2026-07-26:

- **`ShaderEffect` was added to the `Effect` union in 1.131.0** and is absent from 1.125.0. Its shape is `{type: 'SHADER', visible: boolean, id: string, properties?: {[defId: string]: ShaderPropertyValue}}`.
- **The live runtime already accepts it.** A `style_manage` validation failure on channel `zgkx` enumerated Figma's accepted effect variants and included `SHADER` with a required `id` — so the runtime is a superset of the pinned contract.
- **Every other `Effect` variant is unchanged across the six versions**, except one additive field: `noiseSizeVector?: Vector` on `NoiseEffectBase` and `TextureEffect`.
- **The plugin source type-checks cleanly against 1.131.0** — `tsc --noEmit -p figma_plugin/tsconfig.json` reports **0 errors** (measured by swapping the declaration file into `node_modules` and restoring it). The bump has no blast radius on the type gate.
- **The v2.3.3 parity test fails under 1.131.0**, exactly as designed: it detects the eighth union member and demands the schema catch up. The lever is demonstrated, not assumed.

Consequence today: an agent cannot write a `SHADER` effect through `style_manage`, and — more realistically — cannot round-trip a style whose effects already contain one. Before Q35 the catchall would have forwarded it; enumeration traded that forward compatibility for first-call correctness, which is the intended trade, but it leaves this gap until the pin moves.

**Why this is a release of its own rather than a v2.3.3 patch.** `figma_plugin/utils/nodeFields.generated.ts` is auto-generated from these typings (`gen:node-fields`, run inside `build:all`, enforced by `check:generated`). Bumping regenerates `NODE_DATA_FIELDS`, which changes **which node properties `node_info` can read** — additive in all likelihood, but a live behaviour surface, and a diff that deserves review on its own merits rather than riding along inside a release whose scope guard (v2.3.3 D4) forbids unrelated refactors.

### Track 3 — reaction reads are lossy and whole-array updates overwrite unobserved state

The two retained prototype tools operate on native Figma Design metadata, but their current contracts are not safe enough to be the sole automation surface:

- **`reaction_list` deletes valid data before returning it.** `getReactions` removes a reaction when either deprecated `reaction.action.navigation` or *any member* of `reaction.actions[]` is `CHANGE_TO`. A multi-action reaction containing one variant swap therefore disappears in full, including its unrelated actions. The filter contradicts the tool's “read reactions” name and makes a successful response impossible to distinguish from a node that genuinely has no such reaction.
- **Read coverage is not truthful.** A missing explicitly requested root and a thrown per-root read are reported only through progress messages, then omitted from the result. `nodesCount` is merely the request-array length, not an inspected-node count. A fresh dedupe set is created for every root, so overlapping roots can return the same descendant repeatedly. A caller cannot prove whether an empty result means “no reactions,” “node absent,” “read failed,” or “duplicate traversal was collapsed downstream.”
- **`reaction_update` is a stale whole-array replacement.** The caller reads an array, edits a local copy, and later supplies the entire replacement to `setReactionsAsync`. Nothing binds that write to the state that was read. A human edit or another agent edit between the two calls is silently overwritten, and any field the schema or caller failed to preserve can be lost with it.
- **The write schema is not the Figma contract.** `NODE.navigation` accepts an arbitrary string; its required nullable `transition` is optional `any`; the three `UPDATE_MEDIA_RUNTIME` variants are collapsed into one arbitrary-string shape; trigger variants do not require their variant-specific fields; transition/easing/vector data are `any`; and variable/expression data admit arbitrary payloads. Conversely, a runtime field added by Figma can be accepted on read yet stripped or rejected on write. The schema therefore neither helps a model compose a valid first call nor guarantees a lossless round trip.
- **Success does not close the observation loop.** `reaction_update` returns only a boolean/message and does not return the authoritative post-write array or a token for the next edit.
- **Setter failures can lose both cause and outcome.** The handler catches the setter rejection as `e` and interpolates `e.message`; a string, `null`, or other non-`Error` throw therefore becomes `Failed to update reactions: undefined`. Live channel `mksu` reproduced this on an official-valid modern `ON_CLICK` → `NAVIGATE` payload, while a later replay of the identical payload succeeded. Because the failed call performed no authoritative read-back before its disposable node was cleaned up, neither “not applied” nor “applied despite rejection” can be claimed. The current boundary therefore loses the original diagnostic and cannot tell an agent whether retry would duplicate, overwrite, or finally apply the intended reaction.

This is a direct Golden Rule issue. First-call correctness requires a complete read plus a discriminated write contract; one-round-trip recovery requires missing/failed coverage, stable refusal codes, and a retry token. A broad full-array setter cannot supply those properties even when callers are told to “read first.”

## Decisions

> [!NOTE]
> **D1 — Taxonomy before conversion; one code per distinct cause-and-recovery, not per site.** Before any site converts, design and review the code taxonomy as its own artifact. The unit of a code is a *cause with a recovery*, so the 313-site rebased baseline must collapse into a bounded set — the working estimate is a few dozen codes, organized by class: missing parameter, invalid parameter value, target not found, wrong target type, state precondition not met (e.g. "no paints to bind"), scope/permission refusals (largely coded already via the guard messages), and relayed sandbox failures. Sites that share a cause share a code; `details` carries the specifics (`parameter`, `nodeId`, `expectedType`, `actualType`, …). Failures relayed from the Figma API itself (for example a `loadFontAsync` rejection) get **`FIGMA_API_ERROR`** with the original message preserved in `details`. A setter rejection becomes `FIGMA_API_ERROR` only after any tool-specific reconciliation proves the authoritative state is exactly the pre-state; D10 exclusively classifies reaction setters whose intended state may have landed despite a reported error, or whose outcome cannot be proven. After this release, `UNKNOWN_ERROR` means only "a bug or a truly unclassifiable state", which is the burn-down target, not zero forever. Codes are permanent identifiers once shipped; the taxonomy review exists because renaming later is a breaking change.

> [!NOTE]
> **D2 — Registry-only origination.** Every conversion replaces an inline throw with a call into the v2.3.3 central registry of message factories; handlers pass operands in and never compose refusal text locally. The 49 central-table throws in the rebased v2.3.3 baseline convert first — they are mechanical (the key already names the code), including the six that interpolate `ERRORS.SCOPE_DELETED` into a template literal, whose appended operand becomes the factory argument — and the legacy `ERRORS` string table is absorbed into the factory registry, with unreferenced keys deleted rather than carried. After conversion, a handler file contains no `throw new Error(` at all.

> [!NOTE]
> **D3 — Message quality gate.** A converted message must pass the v2.3.3 D9 acceptance check: name the cause distinctly, name the read tool that supplies the correct value where one exists, and state the recovery so the correct retry is derivable from the error text and the tool list alone. Messages for conditions with no agent-executable recovery (internal invariants, `FIGMA_API_ERROR`) state that explicitly — "not recoverable by retry; report the error" — which is itself the recovery. Converting a site without bringing its message to standard is not permitted: a code attached to a message that cannot guide recovery is the false affordance Q16 rejected.

> [!NOTE]
> **D4 — Playbook parity, mechanically enforced.** Every code in the registry has an `error-playbook.md` entry and vice versa, checked by a new `check:error-codes` script wired into CI beside `check:suppressions` (same pattern as the `safetyContract.test.ts` bidirectional diff). A code without an entry fails CI; an entry without a code fails CI. Shared-cause codes get one entry each — this is what makes D1's bounded taxonomy affordable where per-site codes would not be.

> [!NOTE]
> **D5 — Tests assert codes, not prose.** The 102 prose assertions migrate in the same phase as the sites they test: identity is asserted via `code` (and `details` where relevant); message *content* is asserted only by the v2.3.3 D9 acceptance tests that exist to pin recovery text. This unfreezes message wording from the test suite — after this release, improving a message is not a test break unless the recovery content changes.

> [!NOTE]
> **D6 — No control-flow change; ratcheted enforcement.** Same conditions throw at the same points; only the thrown value changes. Each Track 1 phase's rebuild diff is reviewed with that rule: any emitted-JS change that is not a throw-site conversion is escalated. A new `check:legacy-throws` script (the `check:suppressions` pattern) counts `throw new Error(` under `figma_plugin/**/*.ts` against a committed baseline that may only decrease — starting at the rebased 313 and ratcheting to 0 as phases land — so the uncoded surface cannot regrow between phases or after release. T2's generated diff and T3's explicitly specified behavior diff are reviewed separately and do not weaken the ratchet.

> [!NOTE]
> **D8 (Track 2) — Bump the pin, let the parity test drive the schema, review the generated diff separately.** Move `@figma/plugin-typings` from `1.125.0` to `1.131.0` and let v2.3.3's Q35 parity test dictate the schema work: it fails on the bump until `SHADER` joins `EFFECT_TYPES` and the discriminated union, which is precisely the mechanism Q35 shipped it for. Three parts, in order.
> - **The bump and its fallout.** Update `package.json` + `package-lock.json`, re-run `gen:node-fields`, and review the regenerated `nodeFields.generated.ts` diff **as its own reviewable unit** — it changes what `node_info` can read, so any field that appears or disappears is justified in the commit message rather than absorbed. `check:types:plugin` is expected to stay at zero errors (measured); if it does not, the new errors are triaged with the v2.3.3 D2 discipline — fix at the source, no suppression — and any that would require a behaviour change stop and escalate.
> - **The `SHADER` variant.** Add `{type: 'SHADER', id: string, visible?: boolean, properties?: record}` to the union, `id` required (Figma requires it and it is not defaultable), `visible` optional per the handler-defaults rule the other variants follow. Add `noiseSizeVector?: Vector` to the `NOISE` and `TEXTURE` variants. `properties` values are `ShaderPropertyValue`, a polymorphic shape whose members include variable bindings — declare it as an open record rather than enumerating it, and record that as a *fourth* entry in the D8 catchall inventory (v2.3.3 Q34's closed list) with the membership rule satisfied: the handler forwards it untouched.
> - **The forward-compatibility question, answered once.** This release does **not** add a general escape hatch for unknown effect types. The alternative considered — a fallback variant that matches any `type` outside the pinned set — was rejected in v2.3.3's Q35 analysis and is rejected again here: to avoid reopening the accept-and-discard hole it would have to exclude the known variants by refinement, which makes every ordinary validation error a two-branch union error, degrading the one-round-trip recovery the enumeration was built to deliver. The pin *is* the forward-compatibility mechanism, and the parity test is what stops it going stale silently. **Standing rule for future variants: bump the typings, let the parity test fail, add the variant.**

> [!NOTE]
> **D7 — One error convention at the MCP boundary.** The UI relay's local dispatch failures are wrapped as coded objects (`UI_RELAY_FAILURE`, original message in `details`) so a UI-side failure is distinguishable from a plugin-authored one. `describeError` survives only as the message-extraction step inside the `UNKNOWN_ERROR` fallback. `channel.ts`'s in-band `status: "error"` envelope is the subject of Q1 (below) — the goal is one convention, but the migration is breaking for callers that read the in-band fields, so it is decided explicitly rather than absorbed silently.

> [!NOTE]
> **D9 (Track 3) — `reaction_list` is lossless, deterministic, and coverage-bearing.** Remove the `CHANGE_TO` filter completely. Read each reaction-capable node's native `reactions` array without normalization, preserving cardinality, array order, the deprecated `action` projection when Figma returns it, `actions`, and any runtime fields the pinned typings do not yet know. Figma represents a component-state change as an action `{type: "NODE", navigation: "CHANGE_TO", ...}`; it is not a separate action type and must not be discarded.
>
> The input requires at least one `nodeId`; IDs are normalized once and duplicate normalized IDs are rejected at the schema boundary. Compute the normalized requested-root set before traversal so `requestedRoot` is independent of traversal order. Traverse in requested-root order and then depth-first Figma child order, using one global normalized-ID set so overlapping roots return each node once; both `[ancestor, descendant]` and `[descendant, ancestor]` input orders are mandatory test cases. `documentDepth` is the live number of parent hops from the containing `PAGE` (`PAGE = 0`, its child `= 1`; `null` only for a detached/unclassifiable node), not depth relative to whichever root reached it first.
>
> Every explicit root that completes its applicable read and canonicalization phases gets a row. The row is `{nodeId, nodeName, nodeType, path, documentDepth, requestedRoot, supportsReactions, reactions, reactionState}`. `path` is the repository's `PathTuple[]`, where each tuple is exactly `[type:string,id:string,name:string]`, ordered from the containing `PAGE` through the immediate parent with the node itself excluded; a `PAGE` and a detached/unclassifiable node use `[]`. `nodes` is emitted in first-encounter order under the requested-root/depth-first traversal defined above. Rows have two exact variants:
>
> - A node outside Figma's reaction mixin surface returns `supportsReactions:false`, `reactions:null`, and `reactionState:null`.
> - A reaction-capable node returns `supportsReactions:true`, its exact array (including `[]`), and an `r1:` token. Descendants are emitted only when reaction-capable and non-empty; an explicitly requested reaction-capable root is emitted even when empty.
>
> The top-level result is `{requestedCount, visitedNodeCount, reactionCapableNodeCount, nodesWithReactions, nodes, coverage}`. `visitedNodeCount` counts unique resolved traversal nodes whether or not they support reactions; `reactionCapableNodeCount` counts nodes whose reaction property was read successfully; `nodesWithReactions` counts emitted reaction-capable rows with a non-empty array. `coverage` is required `{complete, requestedNodeIds, foundRootIds, missingNodeIds, failedNodes}`. `requestedNodeIds` is the normalized input order; `foundRootIds` and `missingNodeIds` are their respective stable subsequences in that same order. Every failed entry is `{nodeId, phase, error:{code,message,details?}}`, and `failedNodes` is appended in first encounter order under the same requested-root/depth-first traversal (including root lookup attempts in requested order). Missing roots and resolution, traversal, reaction-read, or canonicalization failures are named instead of disappearing into progress telemetry; `complete` is true only when every requested root and every visited node completed its applicable phases. A failed root has no fabricated row.
>
> Coverage codes are deterministic rather than falling through to `UNKNOWN_ERROR`: a lookup that resolves to no node uses the Track 1 taxonomy's `NODE_NOT_FOUND`; a thrown lookup, traversal, or reaction-property read uses `FIGMA_API_ERROR` with the normalized original diagnostic and phase; and a value outside the canonical domain uses the T3-specific `REACTION_STATE_UNENCODABLE`, details `{nodeId,phase:\"canonicalize\",paths,reasons}`, whose recovery says the state cannot be safely tokenized or edited through this version—inspect it in Figma and report the runtime shape before retrying. The same unencodable-state refusal blocks `reaction_update` before any setter call. Phase 1 therefore owns **six** T3-specific codes, not five.
>
> `reactionState` is an opaque exact-compare token: `r1:` plus unpadded base64url of the UTF-8 bytes of stable-canonical JSON for `{nodeId,reactions}`. The supported canonical domain is JSON-observable `null`, booleans, strings, finite numbers, arrays, and plain objects. Object keys sort recursively; array order is preserved; JSON number semantics make `-0` canonicalize as `0`. `undefined` values, `bigint`, non-finite numbers, functions, symbols, non-plain objects, and cycles are rejected and reported as a canonicalization coverage failure rather than silently dropped or collapsed. The encoding is injective for this supported canonical JSON domain; it does not claim collision freedom over arbitrary JavaScript values. The implementation must be ES2018/Figma-sandbox-safe with no Node globals. Clients pass the token back verbatim and never construct or interpret it.

> [!NOTE]
> **D10 (Track 3) — `reaction_update` performs one state-checked localized operation.** Remove the public `reactions` replacement field; there is no compatibility alias or hidden full-array mode. Every call requires `{nodeId, nodeName, expectedReactionState, operation}` where `operation` is exactly one member of this wire union, using `op` as its sole discriminator:
>
> - `{op:"INSERT_REACTION", reactionIndex?:number, reaction:{trigger:Trigger, actions:[Action,...]}}` — insert at `reactionIndex` in `0..length`, defaulting to append. Deprecated `action` is forbidden.
> - `{op:"REMOVE_REACTION", reactionIndex:number}` — remove one reaction at `0..length-1`.
> - `{op:"SET_TRIGGER", reactionIndex:number, trigger:Trigger}` — replace only that reaction's trigger. Although reads may expose `trigger:null`, [Figma requires a non-null `Trigger` and at least one action when writing](https://developers.figma.com/docs/plugins/api/Reaction/); removal uses `REMOVE_REACTION`.
> - `{op:"INSERT_ACTION", reactionIndex:number, actionIndex?:number, action:Action}` — insert at `0..effectiveActions.length`, defaulting to append.
> - `{op:"REPLACE_ACTION", reactionIndex:number, actionIndex:number, action:Action}` — replace exactly one action.
> - `{op:"REMOVE_ACTION", reactionIndex:number, actionIndex:number}` — remove exactly one action, but refuse removal of the last effective action; use `REMOVE_REACTION` when the intended result is no reaction.
>
> Every supplied `reactionIndex` and `actionIndex` must be a non-negative finite safe integer (`Number.isSafeInteger(value) && value >= 0`). Enforce this in the SDK schema and repeat it in the plugin before any array access, coercion, clone, or setter call; default insertion indexes come only from the current array length and satisfy the same invariant. Schema-visible violations return the standard MCP `-32602` validation error. The raw plugin defense returns `REACTION_INDEX_OUT_OF_RANGE` with the invalid field and current valid range, omitting the optional offending index value when it is not JSON-safe. Fractional values must never reach `splice`/bracket access, and no layer may truncate, round, clamp, or otherwise coerce an index.
>
> The generic single-node validator returns the one resolved node object; the reaction handler must not resolve it a second time. After every prerequisite `await`, the handler synchronously rechecks the existing `reaction_update` gates—edit permission, exact name, scope ancestry, locked target/ancestor, and reaction capability—plus `expectedReactionState` against that same object. It then clones the live array, derives and validates the candidate, and invokes `setReactionsAsync` once with no intervening lookup, `await`, progress emission, or unrelated callback. Tests inject a rename, reparent, and newly locked ancestor after initial validation and require zero setter calls. This closes the avoidable validation-to-use gaps while acknowledging that Figma exposes no atomic compare-and-set API. T3 adds no instance-interior or INSTANCE-root refusal: the current safety matrix does not impose one, and this release does not change scope/permission behavior; an actual Figma setter rejection on such a node follows the reconciliation contract below.
>
> For any surviving reaction addressed by an action or trigger operation, clone the raw reaction, take a non-empty modern `actions` array as authoritative, otherwise seed an effective action list from a lossless clone of non-null legacy `action`, delete the deprecated `action` field in the **setter candidate**, and set the modern `actions` field before applying the requested patch. This prevents conflicting projections in the value sent to Figma. Every untouched reaction and every untouched field is preserved by deep structural clone, including unknown runtime fields.
>
> Figma may normalize that candidate on read-back. Its official example—and live `mksu`—show an actions-only setter input returning both `actions` and a synthesized deprecated `action` equal to `actions[0]`. Define one narrow `setterEquivalent(actual, intended)` relation: arrays keep exact length/order; objects keep every key/value exactly, except that at each Reaction object where `intended` has no own `action` and has non-empty `actions`, `actual` may have exactly one extra `action` deeply equal to `actual.actions[0]` and `intended.actions[0]`. No other added, removed, defaulted, reordered, or changed field is equivalent. Apply this allowance across the whole returned array because the whole-array Figma setter may normalize untouched reactions too. Return and tokenize the **raw authoritative read-back**, never the projected candidate, and disclose `compatibilityActionIndexes` for every accepted synthesized field. Tests compare all non-allowed structure and canonical values exactly.
>
> Readable state is not automatically writable. Before the setter, every reaction in the final candidate must have a non-null trigger and a non-empty modern actions array. The requested operation may repair or remove the one addressed invalid reaction, but the handler must not normalize unrelated reactions. If any invalid reaction remains, refuse `REACTION_STATE_NOT_WRITABLE` with details `{nodeId,nodeName,currentReactionState,currentNode,invalid:[{reactionIndex,reasons}]}` and zero setter calls. The recovery says to repair/remove the invalid reaction in Figma, or use a targeted operation only when that single operation makes the entire candidate writable; multiple remaining invalid reactions require human cleanup before an API write.
>
> Resolve no-ops before the setter so reconciliation states are disjoint. If the final live pre-state is already `setterEquivalent` to the validated candidate—for example same-value `SET_TRIGGER`/`REPLACE_ACTION`, including a harmless compatibility `action` already synthesized—make zero setter calls and return the success shape below with `noOp:true`, unchanged raw state/token/counts, and `setterReport:{status:\"not_called\",reason:\"NO_CHANGE\"}`. Otherwise `noOp:false` and the table below applies under the invariant that pre-state is not setter-equivalent to intended. Drop `idempotentHint` from `reaction_update`: the tool as a whole is not idempotent because insert/remove operations change state. Replaying a **state-changing** request with its old token must hit `REACTION_STATE_MISMATCH`; replaying a verified no-op with the still-current token may return the same no-op. The description says never to retry an ambiguous outcome automatically and to use the returned authoritative token for the next operation.
>
> Success returns `{success:true,nodeId,nodeName,noOp,operation,beforeCounts,afterCounts,legacyActionMigrated,compatibilityActionIndexes,setterReport,reactions,reactionState}`. `operation` is the normalized requested wire member with default insertion indexes resolved; it does not falsely say an operation was applied when `noOp:true`. Each counts object is `{reactions:number,actionsByReaction:number[]}` using effective-action counts. `legacyActionMigrated` is a required boolean: it is true only when the addressed pre-state lacked a non-empty modern `actions` array, the state-changing candidate seeded that array from a non-null legacy `action`, and authoritative read-back verifies success; it is false for inserts/removing a whole reaction, modern-action edits, every no-op, and every other success. `compatibilityActionIndexes` is a required, unique, strictly ascending `number[]` of reaction indexes at which the authoritative state contains the one permitted synthesized deprecated `action` relative to the candidate used for `setterEquivalent`; it is `[]` when none, and no-op success computes it against the final authoritative pre-setter state and validated candidate exactly as state-changing success computes it against read-back. A state-changing success comes only from authoritative post-write read-back that is `setterEquivalent` to the complete candidate; a no-op success comes from the final synchronous authoritative pre-setter snapshot after every gate/token check. In both cases `reactions` and `reactionState` are raw authoritative state.
>
> The new coded refusals are:
>
> - `REACTION_STATE_MISMATCH`, details `{nodeId,nodeName,expectedReactionState,currentReactionState,currentNode}` where `currentNode` is the same complete reaction-capable row shape returned by `reaction_list`. The message permits recomposing an unambiguous retry directly from this row; call `reaction_list` only if the row is absent/incomplete or concurrency causes another mismatch. Never blindly replay.
> - `REACTION_INDEX_OUT_OF_RANGE`, details `{nodeId,op,reactionIndex?,actionIndex?,invalidField,validRange}` where `invalidField` is exactly `"reactionIndex" | "actionIndex"` and `validRange` is exactly `{minInclusive:number,maxInclusive:number} | null`. Existing-element operations use `0..length-1`, represented as `null` when length is zero; insertion operations use `0..length`. Validate safe-integer form and `reactionIndex` before `actionIndex`, so at most one field/range is reported per refusal. The optional offending index field is included only when its value is a finite JSON-safe number; it is omitted for `NaN`/infinities received through the raw plugin boundary. The message names that same valid range and the non-negative-safe-integer requirement.
> - `REACTION_LAST_ACTION_REMOVAL`, details `{nodeId, reactionIndex}`; the message says to use `REMOVE_REACTION`.
> - `REACTION_STATE_NOT_WRITABLE`, with the invalid-state details and recovery above.
> - `REACTION_STATE_UNENCODABLE`, with the D9 canonicalization details and recovery above.
>
> `setterReport` is an exact JSON-safe union:
>
> - `{status:\"not_called\",reason:\"NO_CHANGE\"}`;
> - `{status:\"resolved\"}`;
> - `{status:\"rejected\",thrownType,message,name?,code?}` where `thrownType` is exactly `\"undefined\" | \"null\" | \"boolean\" | \"number\" | \"string\" | \"bigint\" | \"symbol\" | \"function\" | \"object\"`; or
> - `{status:\"timed_out\",timeoutMs,lateMutationPossible:true}`.
>
> Invoke `setReactionsAsync` inside the same guarded normalization path used for promise rejection. If invocation throws synchronously before returning a promise, classify that value as `setterReport.status:"rejected"` and continue through the same authoritative read-back matrix; it must not bypass the timeout/reconciliation machinery. Snapshot any synchronous throw or asynchronous rejection exactly once. Read `message`, `name`, and `code` at most once each behind separate guards; accept only non-empty strings for optional fields. A directly thrown non-empty string is the message. Otherwise perform at most one guarded `String(origin)` conversion and fall back to a stable non-empty `Figma setReactionsAsync rejected with an unreportable <thrownType> value.` Never return the raw thrown value, literal `undefined` as the message, or let diagnostic formatting prevent read-back. This normalized report appears on reject-plus-success output and every applicable error detail.
>
> Bound `setReactionsAsync` inside the plugin with an implementation timeout shorter than the transport's 30-second inactivity timeout (initial behavior: 20 seconds; tunable without changing the public contract). Consume any late settlement so it cannot produce an unhandled rejection, but do not emit a second result. A timeout still triggers immediate guarded read-back for evidence, yet it always returns `REACTION_UPDATE_OUTCOME_UNKNOWN` with the timed-out report, `outcomeUnknown:true`, `lateMutationPossible:true`, and before/intended/current state when readable: the uncancelled Figma promise may mutate after that snapshot, so even a current pre-state is not clean failure evidence. The message forbids automatic retry and requires the user to close/reopen the plugin execution context, then call `reaction_list` before deciding the next operation.
>
> For a setter that settles before that bound, always classify by authoritative read-back:
>
> | Setter report | Read-back is setter-equivalent to intended | Read-back exactly equals pre-state | Read-back is other readable state | Read-back is unreadable |
> | :- | :- | :- | :- | :- |
> | resolves | verified success | `FIGMA_API_ERROR` (`setterResolvedWithoutApplying:true`) | `REACTION_UPDATE_OUTCOME_UNKNOWN` with `partialMutation:true` | `REACTION_UPDATE_OUTCOME_UNKNOWN` with `outcomeUnknown:true` |
> | rejects | verified success carrying the normalized rejected `setterReport` | clean `FIGMA_API_ERROR` carrying that report | `REACTION_UPDATE_OUTCOME_UNKNOWN` with `partialMutation:true` | `REACTION_UPDATE_OUTCOME_UNKNOWN` with `outcomeUnknown:true` |
>
> Unknown-outcome details include the before and intended arrays/tokens plus the current array/token when readable, `whatChanged` when derivable, the normalized setter report, and any read-back error. The message requires `reaction_list` before retry except for the stronger timeout recovery above. A resolved setter is never itself proof of success, and a rejected setter is never itself proof of failure.

> [!NOTE]
> **D11 (Track 3) — lossless reads, strict writes, and typings parity are separate contracts.** The read-side `reactions` payload stays open and passes supported JSON-observable values through verbatim so a newer runtime field is observable and contributes to `reactionState`. The write side is recursively strict and generated or hand-maintained against Track 2's pinned `@figma/plugin-typings@1.131.0` declarations. It uses an outer `z.union`, not a falsely described single discriminated union: several Figma action variants share the same top-level `type`. Nested `UPDATE_MEDIA_RUNTIME` branches discriminate on `mediaAction`; recursive conditional actions use `z.lazy`.
>
> - all `Action` variants, including three distinct `UPDATE_MEDIA_RUNTIME` shapes, exact `Navigation`, required nullable `NODE.transition`, and the recursive `CONDITIONAL` action tree;
> - every `Trigger` variant with its required variant fields (`timeout`, `delay`, `deprecatedVersion`, `device`/`keyCodes`, or `mediaHitTime`);
> - both transition families, exact direction/easing enums, cubic-bezier and spring parameter shapes, and `overlayRelativePosition`;
> - recursive `VariableData`, `VariableDataType`, expressions/functions, variable aliases, and color values.
>
> A typings-parity test follows the aliases/unions in `plugin-api-standalone.d.ts` and fails when any discriminant or required field drifts. It also compares the Reaction/Action/Trigger/Transition/VariableData declaration surface between `1.125.0` and `1.131.0` and records the measured unchanged/changed result rather than assuming the effect-only bump left it stable. Schema tests cover every action and trigger variant plus recursive conditionals, reject unknown keys at every write depth, and assert precise issue paths plus recovery text for wrong `NAVIGATE` fields, missing transitions, invalid media branches, and nested conditional failures. Untouched raw entries never pass through the strict authoring schema or an allowlist.

## Open questions

**Q1 (v2.3.4) — Does `channel.ts` converge on the v2.3.3 D9 boundary surface?** Today `channel_join` reports failure in-band: a successful tool result with `status: "error"` + `errorCode`/`errorMessage`. Everything else after v2.3.3 fails with `isError: true` + `structuredContent.error`. *(Updated per v2.3.3 Q20, resolved 2026-07-18 Option A: the pass-through repair landed in v2.3.3 — structured codes arrive in `errorCode` verbatim, assigned at origin, with no prose classification — so this question now reduces to the envelope shape alone.)*

- **Option A — converge.** `channel_join` failures become v2.3.3-D9-shaped errors like every other tool; the in-band fields are removed. One convention for agents to learn; breaking for any caller reading the in-band fields, with a CHANGELOG before/after.
- **Option B — keep the dual surface, documented.** `channel_join` keeps its envelope (join is arguably a status report, not a refusal); the guides document the exception explicitly.
- **Recommendation: Option A.** The shared criterion (first-call correctness, one-round-trip recovery) favors one learnable convention over a documented exception, and the breaking cost is small: the guides already teach reading `channel_join`'s result as a whole, and the hard-cutover precedent (v2.3.3 Q8) applies — an exception preserved for compatibility is an exception agents must be taught forever.
